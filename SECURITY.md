# Security

## Security Goals

- Protect tenant data, contact data, property records, provider credentials, consent records, DNC/suppression data, communications, call recordings, transcripts, mail artifacts, prompts, and audit logs.
- Prevent cross-tenant access.
- Prevent compliance bypass by UI, API, workers, MCP tools, AI agents, Telegram/mobile, or voice systems.
- Prevent hidden prompt/prefix leakage.
- Keep hosted AI optional and data-minimized.
- Keep live outreach blocked unless prerequisites and approvals are satisfied.
- Keep third-party licensing/provenance risk visible.

## Threat Model Summary

Primary threats:

- Cross-tenant data leakage.
- Provider credential theft.
- Raw DNC data exposure.
- Unauthorized campaign launch.
- AI tool misuse.
- AI voice misrepresentation.
- Hidden prompt leakage.
- Prompt injection through lead notes, vendor payloads, transcripts, Telegram messages, or CSV imports.
- Compliance gate bypass.
- Unsafe migrations or production data loss.
- Secrets committed to git.
- Provider webhook spoofing.
- Overly broad Telegram/mobile permissions.
- Dependency vulnerabilities or license violations.

## Authentication Rules

Default path:

- Built-in auth for budget/self-host mode.
- Keycloak/authentik optional self-host SSO.
- Ory/Auth0/WorkOS/Okta optional adapters.

Rules:

- Authentication must be required for dashboard, API, Telegram linking, provider settings, exports, campaigns, voice controls, and AI tools.
- Session/token behavior must be documented in `SPEC-005-auth-and-permissions.md`.
- 2FA is required for high-risk actions:
  - Campaign launches.
  - Provider credential changes.
  - DNC settings changes.
  - Telegram account linking.
  - Offer/counteroffer sends.
  - Purchase agreement sends.
  - Changes to offer price, contingencies, close date, or seller credits.

Implemented EP-006 baseline:

- Built-in sessions are HMAC-signed, `HttpOnly`, `SameSite=Strict`, absolute-expiring, and idle-expiring. Staging/production cookies are also `Secure`.
- Every session creation produces a separate double-submit CSRF value; the readable CSRF cookie contains no session credential.
- Staging/production startup rejects placeholder signing/encryption secrets and local/wildcard CORS origins.
- High-risk actions require both session MFA and a current tenant/action-matched approval. Approvals expire after 15 minutes by default.
- The runtime step-up verifier is deny-all until an owner configures a real adapter; the deterministic adapter is test/local-only.

## Authorization Rules

RBAC must include tenant, team, role, permission, and integration scope.

Implemented baseline permission constants are defined once in `packages/domain/src/permissions/permissions.ts`: property/contact/lead read-write-delete/import, campaign read-create-launch, task read-write, offer create-submit, compliance read-override, approval read-grant, provider manage, AI query/action, admin access, and import/export. Roles are `admin`, `manager`, `member`, `viewer`, and `agent`; unknown roles and permissions deny by default.

Rules:

- Deny by default.
- Every tenant-owned query must include tenant scope.
- Provider credentials must be scoped by tenant and integration.
- AI/MCP tool scopes must be narrower than the user's permissions.
- Workers must carry tenant context and authorization-relevant job metadata.

## Input Validation Rules

Validate at every trust boundary:

- API requests.
- Webhooks.
- CSV uploads.
- Provider payloads.
- Telegram commands.
- Mobile push actions.
- Voice transcripts and DTMF inputs.
- AI tool arguments.
- MCP tool requests.
- Search filters.
- File uploads.
- Environment variables.

Validation must reject:

- Unknown enum values.
- Missing tenant scope.
- Invalid phone/email/address formats.
- Campaign launch without compliance prerequisites.
- High-risk action without approval path.
- Prompt/tool arguments that try to expose hidden prefixes.
- Raw DNC export requests.

## Output Encoding Rules

- UI must escape user-provided content.
- Email/direct-mail templates must sanitize merge fields.
- Logs must serialize structured fields safely.
- AI responses must pass sanitizer before user display.
- Streaming AI output must be buffered and sanitized before rendering.
- Markdown or HTML generated by AI must be sanitized before display.

## Secret Management Rules

Secrets include:

- Database URLs.
- JWT/session secrets.
- Provider API keys.
- SMTP credentials.
- DNC credentials.
- MLS/provider tokens.
- Telephony credentials.
- Object storage credentials.
- LLM provider keys.
- Telegram bot token.
- Encryption keys.

Rules:

- Never commit secrets.
- Use `.env.local` for local development and keep it gitignored.
- Use a secret store for staging/production.
- Encrypt provider credentials at rest.
- Redact secrets from logs and errors.
- Rotate compromised secrets.
- Do not print secrets in scripts.
- Environment variable additions must be documented in `ENVIRONMENT.md`.

## Dependency Security Rules

- Use lockfiles.
- Run dependency audit.
- Run secret scan.
- Run SAST where configured.
- Run container scan where images exist.
- Review license obligations before commercial distribution.
- GPL/AGPL/copyleft services are optional sidecars unless legal review approves bundling.
- Do not bundle/fork/modify RTK until ADR-approved license/provenance review exists.
- The persistence package uses the MIT-licensed `pg` client behind `DbConnection`;
  repositories use parameterized values and fixed, code-owned table/column names.
- Production PostgreSQL connections must enable verified TLS. Database URLs and
  credential payloads remain secret and must never appear in logs or test output.

## Logging Redaction Rules

Never log:

- Passwords.
- Session tokens.
- Provider tokens.
- SMTP passwords.
- DNC credentials or raw DNC numbers.
- Raw call recordings.
- Full transcripts containing sensitive data unless stored in secure transcript store.
- Raw compiled prompts or hidden prefixes.
- Payment details.
- Production exports.
- Personal contact details beyond minimal identifiers.

Allowed log identifiers:

- Tenant ID.
- User ID.
- Request ID.
- Job ID.
- Provider route.
- Prefix hash/version.
- Compliance reason code.
- Entity IDs.
- Redacted contact point hash.

## Data Protection Rules

- Tenant data must be isolated.
- Sensitive columns must be encrypted or strongly protected.
- Object storage keys must include tenant scope.
- Access to recordings/transcripts/mail proofs/provider payloads must require tenant permission.
- Hosted LLM payloads must be minimized and optional.
- Raw data is authoritative.
- Token-compressed context is derived and non-authoritative.
- Retention policies must be configurable for recordings, transcripts, prompts/responses, provider payloads, campaign logs, exports, and artifacts.

## Production Data Rules

- Do not use production data in tests.
- Do not run destructive migrations without explicit permission.
- Back up before migrations.
- Verify restore path before launch.
- Do not export raw DNC data.
- Do not use production contacts for smoke tests.
- Do not send live campaigns from default CI or local tests.

## Safe Migration Rules

- Prefer additive migrations.
- Include down migration or documented restore path.
- Backfill in batches.
- Preserve tenant scope.
- Test migrations on synthetic data.
- Do not rename/drop columns containing production data without a migration plan and backup verification.
- Production migrations are STOP conditions unless explicitly permitted.

## API Security Rules

- Validate all requests.
- Authenticate all non-public endpoints.
- Enforce RBAC.
- Enforce tenant scope.
- Use rate limits on auth, search, imports, exports, AI, and campaign endpoints.
- Verify provider webhook signatures where providers support signatures.
- Normalize provider payloads before processing.
- Return stable errors without stack traces in production.
- Include request IDs.

## CSRF / CORS / Session Rules

- If cookie sessions are used, enable CSRF protection for state-changing requests.
- Set `HttpOnly`, `Secure`, and `SameSite` cookie attributes in production.
- Configure CORS allowlists per environment.
- Do not allow wildcard CORS with credentials.
- Session expiration and refresh behavior must be tested.

EP-006 enforces double-submit CSRF checks for state-changing cookie-authenticated API requests. Credentialed CORS uses only the typed `CORS_ALLOWED_ORIGINS` allowlist. The API emits deny-by-default CSP/frame/content-type/referrer/permissions/cross-origin/cache headers, and emits HSTS only in staging/production.

## Rate Limiting and Abuse Prevention

Rate limit:

- Login attempts.
- Password resets.
- Search endpoints.
- CSV import.
- Exports.
- AI chat/tool calls.
- Campaign launch.
- Provider sends.
- Telegram/mobile commands.
- Webhook ingestion bursts.

Abuse controls:

- Provider quotas per tenant.
- Campaign throttles.
- Daily/monthly spend limits.
- Cost alerts.
- Worker backpressure.
- Fraud/spam detection for outreach channels.

EP-006 provides a single-process baseline limiter for auth, import/export, AI, campaign, and webhook routes with stable `RATE_LIMITED` errors and standard rate-limit response headers. It is intentionally not a distributed quota system; multi-instance production requires a shared store in a later operations plan.

## File Upload Rules

- Limit file size.
- Allow only expected MIME types.
- Treat MIME headers as untrusted.
- Store uploads in tenant-scoped object storage.
- Virus scan in production where feasible.
- Parse CSV safely with row limits and preview.
- Never execute uploaded files.
- Redact uploaded data in logs.

## AI and MCP Security Rules

- AI agents must not call arbitrary backend APIs.
- AI tool use must go through MCP Gateway.
- MCP Gateway must enforce policy, tenant scope, permissions, tool schemas, and approval requirements.
- High-risk AI actions return `allowed`, `blocked`, or `needs_approval`.
- Model output is never the source of compliance truth.
- Hidden prefixes must be sanitized.
- Prompt injection content from notes, transcripts, CSV, vendor payloads, and messages must be treated as data, not instructions.
- AI voice must deterministically handle "remove me", "do not call", "stop", "wrong number", "call me later", "transfer me", and "are you a bot?"

## STOP Conditions for Security-Sensitive Actions

Stop when:

- A live credential is required but missing.
- A legal/compliance judgment is required but not specified.
- A migration can destroy production data.
- A provider terms/license question affects implementation.
- A requested feature exposes raw DNC data.
- A requested AI action can make binding commitments without approval.
- A requested change bypasses compliance checks.
- A secret appears in files, logs, tests, or diffs.
